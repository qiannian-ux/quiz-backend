## 0. 背景与目标

当前小程序只有一套 MBTI 测评，功能点（广告、打赏、付费解锁、深度解读）已能跑通。但产品方向已经明确要"加厚度"：多测评合集（九型 / 大五 / 霍兰德 / 恋爱依恋 / EQ 等）+ AI 个性化解读。

现状代码在"单测评"假设下写得很好，但每加一个测评、每加一类结果展示，都要改动多处文件、复制大量模板。这就是用户感知到的"不方便扩展功能"。

**本次重构的硬性约束（不可破坏）**：
- 静默登录失败不影响主流程（游客照样能测完）。
- 本地题库兜底（`data/questions.js`）必须保留 —— 后端挂了用户仍有得玩。
- 密钥/签名逻辑绝不进前端（虚拟支付由后端 `/api/pay/order` 签名）。
- 双端（微信 + 抖音）uni-app 一套代码出包，平台差异走条件编译或适配层，不要散落各页面。

## 2. 为什么"不方便扩展功能"（痛点，附代码证据）

### 痛点 2.1 测评被硬编码为单一 `mbti`

`api/quiz.js` 顶部常量 `QUIZ_CODE = 'mbti'`，`useQuiz.fetchRemoteQuestions()` 和 `submitQuiz()` 都直接引用它。

**后果**：加第二套测评（如霍兰德），至少要改 `api/quiz.js`、`useQuiz.js`、`result.vue` 的展示、`index.vue` 的入口。MBTI 的维度对（`E/I`、`S/N`、`T/F`、`J/P`）和类型描述写死在 `scoring.js` 与 `data/questions.js` 的 `PERSONALITY_TYPES` 里 —— 其他测评的维度模型（如九型的 9 种）根本装不进去。

**一句话**：现在"测评"不是一个可插拔的数据概念，而是一堆散落各处的 `mbti` 特例。

### 痛点 2.2 结果页是巨型页面（667 行）

`pages/result/result.vue` 把以下全部堆在一个文件里：
- 结果主卡（hero）
- 描述卡（desc）
- 维度占比条（bars）
- 小贴士（tip）
- 打赏卡（reward，仅微信）
- 深度解读卡（deep，解锁后）
- 解锁区（unlock：看广告 / 付费）
- 操作区（再测一次 / 回首页）
- 分享（微信 + 抖音各自 `#ifdef`）

**后果**：
- 每加一种结果展示形态（雷达图、名人类比、职业建议），这个文件继续膨胀，冲突概率陡增。
- 展示逻辑、付费逻辑、广告逻辑耦合，任何一处改坏都影响整页。
- 无法复用"卡片"到其他页面（如首页预览卡、好友配对报告）。

### 痛点 2.3 没有统一的导航 / 路由层

`pages.json` 只有 3 个页面，`uniIdRouter` 为空 `{}`。跳转散落各处：
- `index.vue`：`uni.navigateTo({ url: '/pages/quiz/quiz' })`
- `result.vue`：`uni.redirectTo` / `uni.navigateBack` / `uni.reLaunch`

**后果**：加"测评合集首页 → 选测评 → 答题 → 结果 → 分享海报"这类多步流程时，跳转逻辑、登录前置、参数传递都要在每页手写，易漏、易错、难统一拦截（如"未登录不能看历史记录"）。

### 痛点 2.4 功能开关 `FEATURES` 是摆设

`config/env.js` 里 `FEATURES = { wxCloud: true }`，但：
- `utils/cloud.js` 末尾的 `syncFeatures()`（从后端 `GET /api/config` 拉开关覆盖本地）只是 **TODO**，未实现；
- 抖音端广告（穿山甲）在 `utils/ads.js` 底部也是 **TODO**；
- `FEATURES.wxCloud` 当前实际没有被任何"运行期配置"覆盖。

**后果**：想"灰度某个测评""临时关掉付费""抖音端用穿山甲替代微信广告"，现在只能改代码重新发版，没法运维期控制。

### 痛点 2.5 后端算分链路是"死代码"

`useQuiz.submitQuiz()` 会调 `submitAnswers(payload)` 交后端算分，且 `scoring.js` 导出了 `fromServerResult(res, answers)` 把后端结果转成前端结构。但：
- `pages/quiz/quiz.vue` 的 `onNext` 只 `storage` 存 answers 然后跳结果页，**没调 `submitQuiz`**；
- `result.vue` 的 `onMounted` 直接 `calcResult(answers)` 本地算分，**没用 `fromServerResult`**；
- 因此 `submitQuiz` / `fromServerResult` 写了却没接到主流程。

**后果**：后端已具备 `POST /api/quiz/submit`（见 `QuizController`）的权威算分能力，但前端没用上 —— 既浪费了"防篡改成绩"的安全设计，也让"后端算分 + 前端兜底"的双轨策略悬空。

### 痛点 2.6 平台差异处理碎片化

`#ifdef MP-WEIXIN` 散落在 `result.vue`（打赏、付费、分享）、`utils/payment.js`、`utils/ads.js`。抖音端目前只有占位 TODO。

**后果**：每加一个平台相关能力（如抖音分享海报、抖音激励视频），要在多个文件补 `#ifdef MP-TOUTIAO`，容易漏、容易两端行为不一致。缺少一个"平台能力适配器"把差异收敛到一处。

### 痛点 2.7 跨页数据靠 storage 拼大对象

`quiz.vue` 把整份 `answers` 写进 `uni.setStorageSync('quiz_answers')`，`result.vue` 再读出来算分。

**后果**：
- 大对象塞 storage，类型/结构无契约，页面间隐性耦合；
- 用户中途退出再进、或"再测一次"清理不干净，容易串数据；
- 将来要做"历史记录""好友配对"，同一份会话数据会被多处重复发明。

## 3. 重构需求（明确要做到什么）

> 每条需求含"验收标准"，评审通过后即作为实现 Checklist。

### R1 · 配置驱动的多测评（核心需求）

**需求**：把"测评"抽象成可注册的数据实体。加一套新测评 = 在注册表里加一项数据（含题目拉取 code、维度模型、结果描述、展示模板），**不改动** `useQuiz`、`result` 页面骨架、导航层。

**验收标准**：
- 存在 `config/quizzes.js` 测评注册表；新增测评只需追加一条配置即可在"合集首页"出现并被作答。
- `useQuiz` 不再引用任何写死的 `mbti` 常量，改为接收 `quizCode` 参数。
- 维度模型（维度对、类型描述、配色）按测评隔离，MBTI 的 4 对维度定义不再全局硬编码于 `scoring.js`。
- 本地兜底题库支持多套（`data/questions.<code>.js` 或统一索引），按 `quizCode` 取。

### R2 · 结果页组件化拆分

**需求**：`result.vue` 拆为"容器 + 若干可复用卡片组件"，卡片按是否在结果中出现进行组合。

**验收标准**：
- 结果页主文件控制在 ~150 行以内，只负责组装与数据分发。
- 至少拆出：`ResultHero`、`ResultBars`、`ResultDeep`、`RewardCard`、`UnlockCard`、`ResultActions` 等独立组件。
- 卡片组件可被首页预览、好友报告等其他页面复用。

### R3 · 统一导航 + 登录守卫

**需求**：提供统一跳转入口与可选的"需登录"路由守卫，集中处理跳转动效、参数、登录前置。

**验收标准**：
- 所有页面跳转经 `navigators/router.js`（或等价封装），不再出现裸 `uni.navigateTo`。
- "需要登录才能看历史记录 / 好友配对"这类页面可声明式挂守卫，未登录自动走静默登录或引导。
- 多步流程（合集 → 选测评 → 答题 → 结果 → 海报）的流转参数有统一约定。

### R4 · 后端驱动的功能开关

**需求**：运维期可通过后端 `GET /api/config` 控制功能开关（某测评是否上线、付费是否开启、广告位、云能力），前端首次拉取后缓存、离线兜底。

**验收标准**：
- 实现 `utils/cloud.js` 中已规划的 `syncFeatures()`，启动期拉取并覆盖本地 `FEATURES`。
- 支付、广告、某测评入口是否展示，均读 `useFeatures()` 而非写死的 `env.FEATURES`。
- 拉取失败不影响主流程（回退本地默认值）。

### R5 · 打通后端算分（或显式决策）

**需求**：二选一，不许悬空——
- **方案 A（推荐）**：答题完成先 `submitQuiz()` 交后端权威算分；失败再 `calcResult` 本地兜底。`result.vue` 读后端结果（走 `fromServerResult`）。实现"防篡改成绩"初衷。
- **方案 B**：若坚持纯前端算分（如为省一次请求），则**删除** `submitQuiz` / `fromServerResult` / 后端 `submit` 调用，并在文档中写明理由，避免死代码误导。

**验收标准**：后端算分链路要么全通、要么全删，文档与代码一致。

### R6 · 平台能力收敛到适配层

**需求**：把"支付 / 广告 / 分享 / 云能力"的差异收敛到 `services/platform.js`（或独立 service 模块），页面只调统一接口，不写 `#ifdef`。

**验收标准**：
- `result.vue` 内的 `#ifdef MP-WEIXIN` 大幅减少（仅剩无法抽象的模板差异）。
- 抖音端广告 / 分享有可用占位实现（即便先返回 false/null，也不报"方法不存在"）。
- 新增平台能力时，改动集中在适配层，不扩散到页面。

### R7 · 跨页会话数据契约化

**需求**：用轻量会话 store（reactive 单例即可，不必引入 Pinia）承载"当前测评会话"（quizCode、answers、result），替代 storage 拼大对象。storage 仅用于持久化（历史记录、premium 标记）。

**验收标准**：
- 答题 → 结果 的流转不再依赖 `setStorageSync('quiz_answers')` 大对象。
- 会话数据结构有清晰注释 / 类型约定，跨页面不会串。

### 非目标（本次不做）

- 不重写后端（后端接口已满足，仅可能新增 `GET /api/config`）。
- 不引入重型状态库（Pinia）除非后续确实必要。
- 不变更视觉风格（马卡龙 / 治愈系配色、圆点美学保留）。
- 不新增测评内容本身（R1 只搭框架，题库内容由用户后续填）。

### 4.2 关键模块设计

**(a) 测评注册表 `config/quizzes.js`（R1 核心）**

```js
// 新增测评 = 追加一项，页面/逻辑零改动
export const QUIZZES = {
  mbti: {
    code: 'mbti',
    title: 'MBTI 性格测评',
    questionCount: 24,
    // 维度模型：从 scoring.js 的全局常量搬到这里，按测评隔离
    dimensions: [...],
    // 结果类型描述：从 PERSONALITY_TYPES 搬到这里
    types: [...],
    // 本地兜底题库标识
    localSource: 'mbti'
  },
  holland: { /* 霍兰德：后续填 */ }
}
export function getQuizMeta(code) { return QUIZZES[code] || null }
```

**收益**：`useQuiz` 改为 `useQuiz(quizCode)`，`quiz.vue` / `result.vue` 全部从 `getQuizMeta(code)` 取维度与类型，MBTI 不再是特例。

**(b) 统一导航 `navigators/router.js`（R3）**

```js
export function goQuiz(quizCode) {
  quizSession.start(quizCode)           // 初始化会话
  uni.navigateTo({ url: `/pages/quiz/quiz?code=${quizCode}` })
}
export function goResult() {
  uni.navigateTo({ url: '/pages/result/result' })
}
// 守卫示例：需登录才能进的页面
export function guardLogin(next) {
  return isLoggedIn() ? next() : silentLoginThen(next)
}
```

**(c) 功能开关 `useFeatures`（R4）**

```js
// App 启动：await syncFeatures() 拉 GET /api/config 覆盖本地默认值
const features = useFeatures()
if (features.payEnabled) showUnlock()      // 付费入口由开关控制
if (features.quizzes.xxx) showEntry('xxx') // 某测评是否上线
```

**(d) 结果页组件化（R2）**

`result.vue` 只做：
```vue
<ResultHero :info="result.info" />
<ResultBars :bars="bars" />
<ResultDeep v-if="premium" :text="result.info.deep" />
<RewardCard v-if="features.payEnabled" @reward="rewardAuthor" />
<UnlockCard v-if="features.payEnabled && !premium" @ad="unlockByAd" @pay="unlockByPay" />

```

**(e) 平台适配层 `services/platform.js`（R6）**

```js
// 页面只调 pay.buyProduct / ads.showRewarded，内部按端分发
```

## 5. 实施分期（建议里程碑）

| 阶段 | 内容 | 交付物 | 风险 |
|------|------|--------|------|
| **P0 地基** | R1 测评注册表 + `useQuiz(quizCode)` 改造 + 本地题库按 code 取 | 多测评框架可用，MBTI 仍正常 | 改动面广，需回归 MBTI |
